# Final Report on #417 and #425 Status

I have completed the repository audit requested in #425 against the latest `main` branch.
The majority of the Job model and persistence architecture (Phase 1/2) is robustly implemented, but several significant UI/lifecycle decoupling requirements from Phase 3 remain incomplete.

## 2. Re-evaluation of ErrorsModel and QueueModel
Neither `ErrorsModel` nor `QueueModel` own or move the only durable Job record. As shown in `src/queuemodel.cpp` and `src/errorsmodel.cpp`, file persistence (`save()`) explicitly halts if migration has completed (`MigrationOrchestrator::isMigrated()`). Both models function entirely as in-memory data structures populated dynamically by `MainWindow::syncModelsFromJobStore()`.
However, there are still legacy code patterns where failures temporarily append data into `ErrorsModel` or remove items from `QueueModel` (e.g. `QueueModel::removeItem(0)`), causing an unrequested UI glitch until `syncModelsFromJobStore()` runs and rebuilds everything from the authoritative `JobStore`. Therefore, while they don't own the lifecycle representation, their implementation still contains remnants of the old pipeline that need to be fully decoupled.

## 3. Discovered Issues & Issue State Reconciliation

The issues #404 and #402 are closed, while #417 and #425 remain open.

**Candidate Issue 1: Complete Errors Tab Removal and Job/Global Diagnostics Separation (Completes #417)**
- **Observed Behavior**: `m_errorTab` and `ErrorsModel` remain heavily used as UI presentation layers in `MainWindow`, `SessionWindow`, and `SourceWindow`. `ErrorsModel` acts as a generic list for both operational failures and job errors.
- **Expected Behavior**: Remove `m_errorTab` entirely. Display job-related diagnostics directly on the Job/Attempt detail view, and route global/operational errors to a separate background notification/activity feed.
- **Acceptance Criteria**: `m_errorTab` is removed from `MainWindow`, `SourceWindow`, and `SessionWindow`.

**Candidate Issue 2: QueueModel and ErrorsModel should not be directly mutated by operations**
- **Observed Behavior**: `MainWindow::onGithubRepoCreatedResult` calls `m_errorsModel->addErrorObj()`. `QueueModel::removeItem` is still manually invoked in several flow paths. Since these models no longer control disk persistence, modifying them directly creates local state fragmentation before the next `syncModelsFromJobStore()` triggers.
- **Expected Behavior**: `ErrorsModel` and `QueueModel` should be strict read-only projections. Operations must only mutate `JobData` within `JobStore` and trigger a full sync to update the UI models.
