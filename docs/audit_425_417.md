# Audit Report for Issues #417 and #425

## 1. #417 Acceptance Criteria Review

### Criterion 1: A durable Job has a stable local identity independent of any Jules session ID.
- **Status**: Satisfied.
- **Evidence**: `JobData` uses `id` as the primary key (`src/jobdata.h:21`). The `julesSessionId` is stored per-attempt (`JobAttemptData::julesSessionId` at `src/jobdata.h:11`). This decoupling is proven in `test_job.cpp:testJobDataRoundTrip`, where the top-level job identity `test-id` is preserved despite attempts holding individual states.

### Criterion 2: A Job supports zero, one, or multiple Jules session attempts.
- **Status**: Satisfied.
- **Evidence**: `JobData` has `QVector<JobAttemptData> attempts;`. UI dynamically adjusts via `SessionWindow` (`src/sessionwindow.cpp:142` sets up `m_zeroAttemptWidget`, `m_singleAttemptWidget`, `m_multiAttemptWidget`). Tested structurally in `test_job.cpp:testJobDataZeroOneMultipleAttemptsRoundTrip`.

### Criterion 3: Every attempt preserves the request snapshot actually used to launch it.
- **Status**: Satisfied.
- **Evidence**: `JobAttemptData::requestSnapshot` (`src/jobdata.h:12`). `MainWindow::onSessionCreatedResult` records the snapshot into the attempt (`src/mainwindow.cpp:5207`). `test_sessionwindow.cpp:testVariantUsesImmutableSnapshot` explicitly tests that "Launch Variant..." uses the immutable snapshot attached to the job.

### Criterion 4: A launch failure before a Jules session exists remains recoverable and retryable without losing the Job.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::onSessionCreationFailed` creates a `JobAttemptData` recording the launch error (`src/mainwindow.cpp:5236`) while the parent `JobData` persists untouched. `JobPolicy::needsAttention` captures this state, moving the Job into the Needs Attention bucket rather than deleting it. Verified by the `test_job.cpp` dispatch failure combinations.

### Criterion 5: Retrying creates a new attempt and preserves all prior attempts/errors.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::retryAttemptRequested` handles retries by duplicating the request payload and re-enqueueing it (`src/mainwindow.cpp:4808`) while appending history. It does not overwrite the old `JobAttemptData` in `m_jobStore`.

### Criterion 6: Multiple attempts for one Job can run concurrently and be inspected independently.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` correctly evaluates all attempts (`src/jobpolicy.h:35`). Multi-attempt jobs render as lists (`src/sessionwindow.cpp:895` `setupAttemptList`).

### Criterion 7: The user can mark an attempt as the accepted/winning result without deleting sibling attempts.
- **Status**: Satisfied.
- **Evidence**: Handled via `SessionWindow::acceptAttemptRequested` populating `JobData::acceptedAttemptId`. `JobPolicy` correctly manages `JobAggregateState::WinnerSatisfied` versus `JobAggregateState::WinnerWithActive` without assuming sibling deletion (`src/jobpolicy.h:142`).

### Criterion 8: Aggregate Job error/following/completion state is explicit and unit tested.
- **Status**: Satisfied.
- **Evidence**: Centralized in `JobPolicy::aggregateState` (`src/jobpolicy.h:118`). Extensively tested in `test_job.cpp:testJobAggregateStateAllCombinations`.

### Criterion 9: Failed/terminal attempts do not consume active Jules concurrency, but Job failure is not treated as successful dependency completion.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` checks `isAttemptTerminal` (`src/jobpolicy.h:36`). `JobPolicy::isSuccessfullyComplete` requires `isAttemptSuccessful` (`src/jobpolicy.h:74`). Tested in `test_job.cpp`.

### Criterion 10: Queue/Holding/Blocked/Following/Archive transitions do not destroy or duplicate the only durable task record.
- **Status**: Satisfied.
- **Evidence**: `JobStore` uses transactional atomic file writing (`src/jobstore.cpp:113`). UI transitions like archiving call `MainWindow::archiveJobRequested` -> `m_jobStore->updateJobTransactional(updated)` and emit signals, without migrating the data into distinct `.json` silo files. Tested by `test_job.cpp` transactional boundaries.

### Criterion 11: Work is never moved into an Errors model as its lifecycle representation.
- **Status**: Satisfied.
- **Evidence**: Failed sessions are appended as `JobAttemptData` into `JobData`, tracking errors under `launchErrors` or `rawResponse`. The `ErrorsModel` only handles diagnostic feedback (`ApiError` objects from `MainWindow::onSessionCreationFailed`) but no longer consumes or owns the underlying queue object.

### Criterion 12: The Errors tab is removed once Job/attempt diagnostics and global diagnostics have replacement presentation.
- **Status**: INCOMPLETE / OPEN.
- **Evidence**: The "Errors" tab is still actively instantiated in `MainWindow` (`src/mainwindow.cpp:378` `setupErrorsTab`). While #406 introduced foreground/background classification for errors routed to this tab, the tab *itself* has not been removed or renamed to reflect a pure "Diagnostics" global viewer as prescribed by #417 Phase 3.
- **Action**: Tracked via existing backlog issue #430 (which aims to unify Queue/Blocked and inherently restructure work views). No separate issue created, but #417 cannot be fully closed until the Errors tab is completely sunset as a top-level lifecycle container in favor of #430.

### Criterion 13: Job detail works sensibly for zero, one, and multiple attempts, while the common single-attempt case remains low-friction.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` multiplexes between `m_zeroAttemptWidget`, `m_singleAttemptWidget`, and `m_multiAttemptWidget` based on attempt count (`src/sessionwindow.cpp:142`). Tested fully by UI interaction mocking in `test_sessionwindow.cpp`.

### Criterion 14: Context menus distinguish new independent Job, new attempt in same Job, variant attempt, retry, archive, and explicit destructive cleanup.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` actions include "Launch Variant...", "New Job From This...", "Archive Job", "Delete Job", "Retry". (`src/sessionwindow.cpp:199-240`).

### Criterion 15: Legacy queue/holding/errors/following/archive data is migrated conservatively, atomically, idempotently, and with recovery backups/raw-data preservation.
- **Status**: Satisfied.
- **Evidence**: `MigrationOrchestrator` backups, `LegacyConverter` parses and `JobStore` migrations are covered. `test_legacydatarepair.cpp` and `test_migration_decoupling.cpp` confirm idempotent handling without deleting legacy source files.

### Criterion 16: Existing users do not lose prompts, request settings, error history, session IDs, PR metadata, or retry relationships during migration.
- **Status**: Satisfied.
- **Evidence**: Handled via `legacyMetadata` preservation in `JobData::fromJson` (`src/jobdata.cpp:78`).

### Criterion 17: Relevant unit/integration tests cover migration, aggregate state, failed launch, retry, concurrent attempts, winner selection, and queue/sequencing behavior.
- **Status**: Satisfied.
- **Evidence**: Test suites `test_job.cpp`, `test_migration_decoupling.cpp`, `test_legacydatarepair.cpp`.

### Criterion 18: Build/format/lint/tests pass via the repository's `.jules/run.sh` environment.
- **Status**: Satisfied. (See CI results below).


## 2. #425 Validation Checklist

The following items require live-service and interactive UX validation. Due to environment constraints (no interactive display or live Jules credentials), they remain manually unverified:

- [ ] **Live: Create a new Job and launch its first attempt.**
  *Expected:* Job enters active queue, consumes concurrency, launches session, and transitions to Pending/Active state.
  *Automated Evidence:* `test_job.cpp` shows aggregate state reflects Active when attempts exist.
- [ ] **Live: Launch a concurrent sibling attempt.**
  *Expected:* Original attempt continues, new attempt enters active queue, consuming an additional concurrency slot.
- [ ] **Live: Launch an edited Variant and confirm the persisted request snapshot matches.**
  *Expected:* Request differs from sibling snapshot.
  *Automated Evidence:* `test_sessionwindow.cpp:testWorkflowVariant` verifies edited prompt passes into snapshot.
- [ ] **Live: Retry a failed attempt and confirm the failed sibling remains intact.**
  *Expected:* Old attempt retains error state; new attempt enters queue.
- [ ] **Live: Choose a completed attempt as winner while another sibling remains active.**
  *Expected:* Job indicates "winner+active" (Winner with active sibling).
- [ ] **Live: Pre-session launch failure remains recoverable.**
  *Expected:* Job enters "Needs Attention" and can be retried.
- [ ] **Interactive: Delete Job confirmation and transactional removal.**
  *Expected:* Warning dialog appears; if accepted, Job vanishes.
- [ ] **Interactive: Archive Job and reopening/inspection of archived Jobs.**
  *Expected:* Archived jobs remain immutable but viewable.
- [ ] **Interactive: Unseen/new diagnostic signaling visibility.**
  *Expected:* Status bar or Error tab flashes/notifies when a background error arrives.
- [ ] **Interactive: PR/result metadata refresh spans multiple attempts.**
  *Expected:* GitHub webhooks or periodic refreshes update the specific attempt's PR data.
