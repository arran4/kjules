# Audit Report for Issues #417 and #425

## 1. #417 Acceptance Criteria Review

### Criterion 1: A durable Job has a stable local identity independent of any Jules session ID.
- **Status**: Satisfied.
- **Evidence**: `JobData` uses `id` as the primary key (`src/jobdata.h:21`). The `julesSessionId` is stored per-attempt (`JobAttemptData::julesSessionId` at `src/jobdata.h:11`). This decoupling is proven in `test_job.cpp:testJobDataRoundTrip`, where the top-level job identity `test-id` is preserved despite attempts holding individual states.

### Criterion 2: A Job supports zero, one, or multiple Jules session attempts.
- **Status**: Satisfied.
- **Evidence**: `JobData` has `QVector<JobAttemptData> attempts;`. `SessionWindow` UI dynamically adjusts to zero, one, or multi-attempt views (`src/sessionwindow.cpp:142` sets up `m_zeroAttemptWidget`, `m_singleAttemptWidget`, `m_multiAttemptWidget`). Tested structurally in `test_job.cpp:testJobDataZeroOneMultipleAttemptsRoundTrip` and integrated via UI assertions in `tests/test_sessionwindow.cpp:testMultipleAttempts` and `testZeroAttempts`.

### Criterion 3: Every attempt preserves the request snapshot actually used to launch it.
- **Status**: Satisfied.
- **Evidence**: `JobAttemptData::requestSnapshot` (`src/jobdata.h:12`). `test_sessionwindow.cpp:testVariantUsesImmutableSnapshot` asserts that "Launch Variant..." uses the immutable snapshot bound strictly to that specific attempt instance (`QCOMPARE(spyVariant.at(0).at(1).toJsonObject().value(QStringLiteral("prompt")).toString(), QStringLiteral("Alpha Prompt"))`).

### Criterion 4: A launch failure before a Jules session exists remains recoverable and retryable without losing the Job.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::onSessionCreationFailed` creates a failed `JobAttemptData` recording the launch error (`src/mainwindow.cpp:5236`), updating the Job in `m_jobStore`. Verified by `test_job.cpp` asserting `JobPolicy::needsAttention` accurately flags it without dequeuing/destroying it, and `test_sessionwindow.cpp:testWorkflowRetry` verifying the failed attempt is preserved and retry action generates a second attempt.

### Criterion 5: Retrying creates a new attempt and preserves all prior attempts/errors.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::retryAttemptRequested` handles retries by duplicating the request payload and appending a new item to `QueueModel` (`src/mainwindow.cpp:4808`). Verified by `test_sessionwindow.cpp:testWorkflowRetry` ensuring the updated Job possesses two distinct attempts `QCOMPARE(updatedJob->attempts.size(), 2)` after a retry.

### Criterion 6: Multiple attempts for one Job can run concurrently and be inspected independently.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` explicitly evaluates each attempt (`src/jobpolicy.h:35`), permitting concurrent tracking. `test_sessionwindow.cpp:testMultipleAttemptsIndependentlySelectable` verifies that multi-attempt tabs allow inspection of sibling tasks and unique attributes without overwriting.

### Criterion 7: The user can mark an attempt as the accepted/winning result without deleting sibling attempts.
- **Status**: Satisfied.
- **Evidence**: Handled via `SessionWindow::acceptAttemptRequested` populating `JobData::acceptedAttemptId`. `test_sessionwindow.cpp:testWinnerEligibility` validates that winning results are recognized, and `test_job.cpp:testJobAggregateStateAllCombinations` verifies `JobAggregateState::WinnerWithActive` correctly handles coexisting siblings.

### Criterion 8: Aggregate Job error/following/completion state is explicit and unit tested.
- **Status**: Satisfied.
- **Evidence**: Centralized in `JobPolicy::aggregateState` (`src/jobpolicy.h:118`). Extensively tested in `test_job.cpp:testJobAggregateStateAllCombinations` assessing all states: NeedsAttention, Pending, Active, ActiveWithFailed, etc.

### Criterion 9: Failed/terminal attempts do not consume active Jules concurrency, but Job failure is not treated as successful dependency completion.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` skips over `isAttemptTerminal` attempts (`src/jobpolicy.h:36`). `JobPolicy::isSuccessfullyComplete` mandates `isAttemptSuccessful` (`src/jobpolicy.h:74`). Evaluated explicitly in `test_job.cpp`.

### Criterion 10: Queue/Holding/Blocked/Following/Archive transitions do not destroy or duplicate the only durable task record.
- **Status**: Satisfied.
- **Evidence**: `JobStore` uses transactional atomic file writing (`src/jobstore.cpp:113`). State transitions like archiving (`MainWindow::archiveJobRequested`) update the global job via `m_jobStore->updateJobTransactional(updated)` and emit signals. Tested in `test_job.cpp` transactional boundaries and `test_sessionwindow.cpp:testArchiveRetainsFullHistory`.

### Criterion 11: Work is never moved into an Errors model as its lifecycle representation.
- **Status**: Satisfied.
- **Evidence**: Failed sessions mutate `JobAttemptData` tracking errors under `launchErrors` within `JobData`. `ErrorsModel` only handles unattached diagnostics (`ApiError` objects) but no longer owns failing jobs.

### Criterion 12: The Errors tab is removed once Job/attempt diagnostics and global diagnostics have replacement presentation.
- **Status**: INCOMPLETE / OPEN.
- **Evidence**: The "Errors" tab is still instantiated as a core layout panel (`src/mainwindow.cpp:378` `setupErrorsTab`). While errors route properly inside the data models, the visual tab has not been replaced or sunset.
- **Action**: Tracked via pending issue submission (see Section 4: Ready-to-file Issues).

### Criterion 13: Job detail works sensibly for zero, one, and multiple attempts, while the common single-attempt case remains low-friction.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` logic routes smoothly among `m_zeroAttemptWidget`, `m_singleAttemptWidget`, and `m_multiAttemptWidget` (`src/sessionwindow.cpp:142`). Tested thoroughly in `test_sessionwindow.cpp` using `testZeroAttempts`, `testOneAttempt`, and `testMultipleAttempts`.

### Criterion 14: Context menus distinguish new independent Job, new attempt in same Job, variant attempt, retry, archive, and explicit destructive cleanup.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` actions include exactly: "Launch Variant...", "New Job From This...", "Archive Job", "Delete Job", "Retry". (`src/sessionwindow.cpp:199-240`). Tested explicitly in `test_sessionwindow.cpp:testActionSignals`.

### Criterion 15: Legacy queue/holding/errors/following/archive data is migrated conservatively, atomically, idempotently, and with recovery backups/raw-data preservation.
- **Status**: Satisfied.
- **Evidence**: Handled robustly by `MigrationOrchestrator` backups, `LegacyConverter` parsing, and `JobStore` migrations. Validated fully in `test_legacydatarepair.cpp` and `test_migration_decoupling.cpp`.

### Criterion 16: Existing users do not lose prompts, request settings, error history, session IDs, PR metadata, or retry relationships during migration.
- **Status**: Satisfied.
- **Evidence**: Extracted gracefully into `legacyMetadata` in `JobData::fromJson` (`src/jobdata.cpp:78`). Verified by `test_legacydatarepair.cpp`.

### Criterion 17: Relevant unit/integration tests cover migration, aggregate state, failed launch, retry, concurrent attempts, winner selection, and queue/sequencing behavior.
- **Status**: Satisfied.
- **Evidence**: Thoroughly verified by integration test suites `test_job.cpp`, `test_migration_decoupling.cpp`, `test_legacydatarepair.cpp`, and `test_queuescheduling.cpp`.

### Criterion 18: Build/format/lint/tests pass via the repository's `.jules/run.sh` environment.
- **Status**: Satisfied. (See CI Results section).

**Issue Title**: Refactor legacy Errors Tab into replacement Global Diagnostics UI
**Body**:
```markdown
Follow-up to #417 (Decouple KJules jobs from Jules sessions) and Phase 3 Job model implementation.

### Observed current behavior
Currently, the legacy "Errors" tab remains instantiated (`src/mainwindow.cpp:378` `setupErrorsTab`) as a core top-level component, despite #417's requirement to remove it as a lifecycle destination. While Job/attempt errors correctly route to `JobAttemptData` and avoid this tab, unattached global diagnostics (e.g. GitHub lookup failures, rate limits) still dump directly into this legacy list view.

### Expected behavior
Per #417 Phase 3 criteria, the "Errors" tab should be completely retired.
Instead, global and unattached source diagnostics should have a distinct, modernized "Diagnostics/Activity" presentation (such as a status overlay, dedicated global notification list, or embedded source-level diagnostic viewer).

### Evidence
- `src/mainwindow.cpp` still initializes `errTab` and `m_errorsView`.
- Global errors (e.g., from `APIManager`) are pushed into `ErrorsModel`, which the `Errors` tab still binds to.

### Distinction from existing issues
- **#430** explicitly handles unifying `Queue` and `Blocked` into a single view. It does not dictate how to tear down the Errors tab or visualize global diagnostic errors.
- **#397** addresses visual exposure of GitHub rate limits, which intersects with this, but does not explicitly tackle the tab replacement.

### Bounded implementation scope
1. Design and introduce a replacement visualization for global operations errors (e.g., a "Diagnostics" log).
2. Repurpose `ErrorsModel` solely to feed this new Diagnostics visualization.
3. Remove `setupErrorsTab` and the top-level "Errors" tab from `MainWindow`.
4. Add basic UI tests verifying global errors appear in the new diagnostic log, decoupled from Jobs.
```
