# Audit Report for Issues #417 and #425

## 1. #417 Acceptance Criteria Review

### Criterion 1: A durable Job has a stable local identity independent of any Jules session ID.
- **Status**: Satisfied.
- **Evidence**: `JobData` uses `id` as the primary key (`src/jobdata.h:21`). The `julesSessionId` is stored per-attempt (`JobAttemptData::julesSessionId` at `src/jobdata.h:11`). This decoupling is proven at the model level in `test_job.cpp:testJobDataRoundTrip`, where the top-level job identity `test-id` is preserved despite attempts holding individual states.

### Criterion 2: A Job supports zero, one, or multiple Jules session attempts.
- **Status**: Satisfied.
- **Evidence**: `JobData` has `QVector<JobAttemptData> attempts;`. `SessionWindow` UI dynamically adjusts to zero, one, or multi-attempt views (`src/sessionwindow.cpp:142`). Tested structurally in `test_job.cpp:testJobDataZeroOneMultipleAttemptsRoundTrip` and integrated via UI mock interactions in `tests/test_sessionwindow.cpp:testMultipleAttempts` and `testZeroAttempts`.

### Criterion 3: Every attempt preserves the request snapshot actually used to launch it.
- **Status**: Satisfied.
- **Evidence**: `JobAttemptData::requestSnapshot` (`src/jobdata.h:12`). `MainWindow::onSessionCreatedResult` binds the snapshot (`src/mainwindow.cpp:5207`). `test_sessionwindow.cpp:testVariantUsesImmutableSnapshot` asserts at the UI/model boundary that "Launch Variant..." uses the immutable snapshot bound strictly to that specific attempt instance. (Note: capturing the exact outbound live-service HTTP request payload to guarantee identicality remains currently **unverified** without live testing).

### Criterion 4: A launch failure before a Jules session exists remains recoverable and retryable without losing the Job.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::onSessionCreationFailed` creates a failed `JobAttemptData` recording the launch error (`src/mainwindow.cpp:5236`), updating the Job in `m_jobStore`. Verified by `test_job.cpp` asserting `JobPolicy::needsAttention` accurately flags it without dequeuing it, and `test_sessionwindow.cpp:testWorkflowRetry` verifying the failed attempt is preserved and retry action generates a second attempt in local tests.

### Criterion 5: Retrying creates a new attempt and preserves all prior attempts/errors.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::retryAttemptRequested` handles retries by duplicating the request payload and appending a new item to `QueueModel` (`src/mainwindow.cpp:4808`). Verified by `test_sessionwindow.cpp:testWorkflowRetry` ensuring the updated Job possesses two distinct attempts locally.

### Criterion 6: Multiple attempts for one Job can run concurrently and be inspected independently.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` explicitly evaluates each attempt (`src/jobpolicy.h:35`), permitting concurrent tracking. `test_sessionwindow.cpp:testMultipleAttemptsIndependentlySelectable` verifies that multi-attempt tabs allow inspection of sibling tasks concurrently. (Note: full live HTTP concurrency requires live testing).

### Criterion 7: The user can mark an attempt as the accepted/winning result without deleting sibling attempts.
- **Status**: Satisfied.
- **Evidence**: Handled via `SessionWindow::acceptAttemptRequested` populating `JobData::acceptedAttemptId`. `test_sessionwindow.cpp:testWinnerEligibility` validates that winning results are recognized, and `test_job.cpp:testJobAggregateStateAllCombinations` verifies `JobAggregateState::WinnerWithActive` correctly handles coexisting siblings without deleting them.

### Criterion 8: Aggregate Job error/following/completion state is explicit and unit tested.
- **Status**: Satisfied.
- **Evidence**: Centralized in `JobPolicy::aggregateState` (`src/jobpolicy.h:118`). Extensively tested in `test_job.cpp:testJobAggregateStateAllCombinations` assessing all states.

### Criterion 9: Failed/terminal attempts do not consume active Jules concurrency, but Job failure is not treated as successful dependency completion.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` skips over `isAttemptTerminal` attempts (`src/jobpolicy.h:36`). `JobPolicy::isSuccessfullyComplete` mandates `isAttemptSuccessful` (`src/jobpolicy.h:74`). Evaluated explicitly in `test_job.cpp` at the policy level.

### Criterion 10: Queue/Holding/Blocked/Following/Archive transitions do not destroy or duplicate the only durable task record.
- **Status**: Satisfied.
- **Evidence**: `JobStore` uses transactional atomic file writing (`src/jobstore.cpp:113`). State transitions like archiving update the global job via `m_jobStore->updateJobTransactional(updated)` and emit signals. Tested in `test_job.cpp` transactional boundaries and `test_sessionwindow.cpp:testArchiveRetainsFullHistory`.

### Criterion 11: Work is never moved into an Errors model as its lifecycle representation.
- **Status**: Satisfied.
- **Evidence**: Failed sessions mutate `JobAttemptData` tracking errors under `launchErrors` within `JobData`. `ErrorsModel` only handles unattached diagnostics (`ApiError` objects) but no longer owns failing jobs queue entities.

### Criterion 12: The Errors tab is removed once Job/attempt diagnostics and global diagnostics have replacement presentation.
- **Status**: INCOMPLETE / OPEN.
- **Evidence**: The legacy "Errors" tab is still instantiated as a core layout panel (`src/mainwindow.cpp:378` `setupErrorsTab`) retaining it formally as a work lifecycle destination. While a clearly labelled, standalone Diagnostics/Activity tab is fully permitted for unattached global errors, the specific legacy requirement to retire the *Errors-as-work-lifecycle destination* itself is unmet.
- **Action**: Tracked actively by **Issue #439**.

### Criterion 13: Job detail works sensibly for zero, one, and multiple attempts, while the common single-attempt case remains low-friction.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` logic routes smoothly among `m_zeroAttemptWidget`, `m_singleAttemptWidget`, and `m_multiAttemptWidget` (`src/sessionwindow.cpp:142`). Tested thoroughly in `test_sessionwindow.cpp` using `testZeroAttempts`, `testOneAttempt`, and `testMultipleAttempts`.

### Criterion 14: Context menus distinguish new independent Job, new attempt in same Job, variant attempt, retry, archive, and explicit destructive cleanup.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` actions include exactly: "Launch Variant...", "New Job From This...", "Archive Job", "Delete Job", "Retry". Tested explicitly in `test_sessionwindow.cpp:testActionSignals`.

### Criterion 15: Legacy queue/holding/errors/following/archive data is migrated conservatively, atomically, idempotently, and with recovery backups/raw-data preservation.
- **Status**: Satisfied.
- **Evidence**: Handled robustly by `MigrationOrchestrator` backups, `LegacyConverter` parsing, and `JobStore` migrations. Validated fully in `test_legacydatarepair.cpp` and `test_migration_decoupling.cpp`.

### Criterion 16: Existing users do not lose prompts, request settings, error history, session IDs, PR metadata, or retry relationships during migration.
- **Status**: Satisfied.
- **Evidence**: Extracted gracefully into `legacyMetadata` in `JobData::fromJson` (`src/jobdata.cpp:78`). Verified by `test_legacydatarepair.cpp`.

### Criterion 17: Relevant unit/integration tests cover migration, aggregate state, failed launch, retry, concurrent attempts, winner selection, and queue/sequencing behavior.
- **Status**: Satisfied.
- **Evidence**: Thoroughly verified by integration test suites `test_job.cpp`, `test_migration_decoupling.cpp`, `test_legacydatarepair.cpp`, and `test_queuescheduling.cpp`.

### Criterion 18: Build/format/lint/tests pass via the repository's `.jules/run.sh` environment.
- **Status**: Satisfied. (See CI Results section).


## 2. #425 Validation Checklist

The following items mandate live-service and interactive UX validation. They remain manually unverified:

- [ ] **Live: Create a new Job and launch its first attempt.**
  *Setup:* Start KJules, connect to valid Jules endpoint. Create a new Job via "New Session".
  *Action:* Dispatch Job from Queue.
  *Verification:* Job consumes a concurrency slot, launches Jules session via HTTP, and transitions to Pending/Active state dynamically in the Following view.
- [ ] **Live: Launch a concurrent sibling attempt.**
  *Setup:* Have a running Active attempt.
  *Action:* Use "Launch New Jules Session for This Job".
  *Verification:* Original attempt continues undisturbed. New attempt enters active queue, consumes an additional concurrency slot if limits permit, and dispatches alongside the original.
- [ ] **Live: Launch an edited Variant and confirm the persisted request snapshot matches.**
  *Setup:* Open a Job with an existing attempt.
  *Action:* Click "Launch Variant...", edit the prompt, and launch.
  *Verification:* Upon dispatch, intercept/verify the outbound API request payload contains the modified prompt, and ensure local inspection of the new attempt reflects this exact variant snapshot differently than its sibling.
- [ ] **Live: Retry a failed attempt and confirm the failed sibling remains intact.**
  *Setup:* Allow an attempt to fail (e.g. rate limit or bad request).
  *Action:* Click "Retry" on the failed attempt.
  *Verification:* Old attempt stays preserved holding the error history visually. A new active attempt enters the queue and attempts dispatch.
- [ ] **Live: Choose a completed attempt as winner while another sibling remains active.**
  *Setup:* Create a Job with two attempts; wait for a remote Jules attempt to complete, leave the other Active.
  *Action:* Select the completed attempt and mark as Winner. Attempt to mark an incomplete (ineligible) attempt as winner.
  *Verification:* Selecting an ineligible attempt should be disabled/rejected. Marking the eligible one sets Job aggregate UI to "winner+active" (Winner satisfies requirement, but an outstanding sibling visually continues).
- [ ] **Live: Pre-session launch failure remains recoverable.**
  *Setup:* Break network connection or mock an immediate 500 error on dispatch.
  *Action:* Dispatch a Job.
  *Verification:* Job reflects "Needs Attention" state, retaining data without destroying the core Job item, and permits retry once the network is restored.
- [ ] **Live: Verify PR/result metadata reloads span multiple attempts visually.**
  *Setup:* Create a multi-attempt Job that interacts with multiple GitHub PRs.
  *Action:* Wait for auto-refresh or trigger manual refresh.
  *Verification:* The specific sibling attempt's PR metadata (merged, closed, etc) correctly routes and updates that specific attempt's UI tab, not bleeding into the sibling.
- [ ] **Live: Failed-only Jobs remain in Following/needs-attention.**
  *Setup:* Create a Job. Force all its attempts to fail.
  *Action:* Refresh Following list.
  *Verification:* The Job must remain visibly listed in Following (flagged for attention) and must not fall off entirely into the Archive or disappear.
- [ ] **Interactive: Job/attempt vs global/source diagnostic discoverability.**
  *Setup:* Generate a Job-specific error (e.g. bad prompt) and a global error (e.g. GitHub rate limit).
  *Action:* Inspect UI.
  *Verification:* Individual attempt errors are readable strictly inside the specific Job's view. The global GitHub API/auth errors show up globally in the main UI status or replacement diagnostic viewer.
- [ ] **Interactive: Delete Job confirmation and transactional removal.**
  *Setup:* Select a Job in Following.
  *Action:* Click "Delete Job". Click "Cancel", then click "Delete Job" and select "Yes".
  *Verification:* On Cancel, the persisted data is left totally intact. Upon "Yes", Job drops entirely from the UI and is removed from `jobs.json` on disk.
- [ ] **Interactive: Archive Job and reopening/inspection of archived Jobs.**
  *Setup:* Archive a 0-attempt, 1-attempt, and multi-attempt Job.
  *Action:* Open them from the Archive tab.
  *Verification:* All three permutations must render read-only inspector views reflecting their distinct states without crashing or rendering empty space.
- [ ] **Interactive: Constraints on mutating archived Jobs.**
  *Setup:* Open an archived Job.
  *Action:* Attempt to click "Launch Variant", "Retry", or modify parameters.
  *Verification:* UI completely disables these mutation actions or intercepts them with a clear error prompt.
- [ ] **Interactive: Zero-attempt history readability.**
  *Setup:* Create a Job, place it on Hold, preventing dispatch.
  *Action:* Double-click to inspect.
  *Verification:* The inspector correctly displays its scheduling configurations, prompt, and error/history log cleanly without a blank "Session" widget.
- [ ] **Interactive: Single-attempt UX friction.**
  *Setup:* Dispatch a normal one-off Job.
  *Action:* Open inspector.
  *Verification:* Workflow behaves virtually identical to the classic Jules single-session windows, directly exposing the session details without heavy multi-tab boilerplate.
- [ ] **Interactive: Unseen/new diagnostic signaling visibility.**
  *Setup:* Force a background operational error (e.g., via polling).
  *Action:* Observe main window.
  *Verification:* Status bar notifications or unread diagnostic counts visibly increment when the background operational error arrives.
- [ ] **Persistence: Reload survival of full Job states.**
  *Setup:* Construct Jobs holding: an accepted winner, active sibling attempts, specific timestamps, local diagnostics, and variant results. Restart KJules.
  *Action:* Re-open the Jobs.
  *Verification:* KJules fully revives all states (winner, siblings, snapshots, history logs) exactly as they were prior to shutdown, directly from `jobs.json`.
- [ ] **Persistence: Migrated-data inspection and backup preservation.**
  *Setup:* Construct an isolated test directory environment (`XDG_DATA_HOME`). Place a legacy `queue.json` and `errors.json` inside it. Start KJules.
  *Action:* Inspect Following/Archive. Check disk.
  *Verification:* The converted jobs successfully load their old properties into the new Job architecture; the raw backup files (`queue.json.bak`, etc.) exist intact on disk.
