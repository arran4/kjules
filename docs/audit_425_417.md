# Audit Report for Issues #417 and #425

## 1. #417 Acceptance Criteria Review

### Criterion 1: A durable Job has a stable local identity independent of any Jules session ID.
- **Status**: Satisfied.
- **Evidence**: `JobData` uses `id` as the primary key (`src/jobdata.h:21`). The `julesSessionId` is stored per-attempt (`JobAttemptData::julesSessionId` at `src/jobdata.h:11`). This decoupling is proven in `test_job.cpp:testJobDataRoundTrip`, where the top-level job identity `test-id` is preserved despite attempts holding individual states. UI persistence logic verifies this ID through `MainWindow` dispatch (`src/mainwindow.cpp:5207`).

### Criterion 2: A Job supports zero, one, or multiple Jules session attempts.
- **Status**: Satisfied.
- **Evidence**: `JobData` has `QVector<JobAttemptData> attempts;`. `SessionWindow` UI dynamically adjusts to zero, one, or multi-attempt views (`src/sessionwindow.cpp:142` sets up `m_zeroAttemptWidget`, `m_singleAttemptWidget`, `m_multiAttemptWidget`). Tested structurally in `test_job.cpp:testJobDataZeroOneMultipleAttemptsRoundTrip` and integrated via UI mock interactions in `test_sessionwindow.cpp:testMultiAttemptTabs`.

### Criterion 3: Every attempt preserves the request snapshot actually used to launch it.
- **Status**: Satisfied.
- **Evidence**: `JobAttemptData::requestSnapshot` (`src/jobdata.h:12`). `MainWindow::onSessionCreatedResult` binds the snapshot (`src/mainwindow.cpp:5207`). `test_sessionwindow.cpp:testVariantUsesImmutableSnapshot` asserts that "Launch Variant..." pre-fills from the immutable snapshot bound strictly to that specific attempt instance.

### Criterion 4: A launch failure before a Jules session exists remains recoverable and retryable without losing the Job.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::onSessionCreationFailed` creates a failed `JobAttemptData` recording the launch error (`src/mainwindow.cpp:5236`), updating the Job in `m_jobStore`. `JobPolicy::needsAttention` accurately flags it without dequeuing/destroying it. Verified by `test_job.cpp` failed dispatch handling and `test_sessionwindow.cpp` interactions against failed-state widgets.

### Criterion 5: Retrying creates a new attempt and preserves all prior attempts/errors.
- **Status**: Satisfied.
- **Evidence**: `MainWindow::retryAttemptRequested` handles retries by duplicating the request payload and appending a new item to `QueueModel` (`src/mainwindow.cpp:4808`). It deliberately does not overwrite `JobAttemptData` in `m_jobStore`, adding a new attempt once processed. Verified sequentially in `test_sessionwindow.cpp:testRetryGeneratesNewAttempt`.

### Criterion 6: Multiple attempts for one Job can run concurrently and be inspected independently.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` explicitly evaluates each attempt (`src/jobpolicy.h:35`), permitting concurrent tracking. `SessionWindow` multi-attempt tabs allow inspection of sibling tasks concurrently via `m_multiAttemptTabWidget` (`src/sessionwindow.cpp:895`).

### Criterion 7: The user can mark an attempt as the accepted/winning result without deleting sibling attempts.
- **Status**: Satisfied.
- **Evidence**: Handled via `SessionWindow::acceptAttemptRequested` populating `JobData::acceptedAttemptId`. `JobPolicy` supports aggregate states `JobAggregateState::WinnerSatisfied` versus `JobAggregateState::WinnerWithActive` preventing sibling erasure (`src/jobpolicy.h:142`). Tested thoroughly in `test_job.cpp:testJobAggregateStateAllCombinations`.

### Criterion 8: Aggregate Job error/following/completion state is explicit and unit tested.
- **Status**: Satisfied.
- **Evidence**: Centralized in `JobPolicy::aggregateState` (`src/jobpolicy.h:118`). Extensively tested in `test_job.cpp:testJobAggregateStateAllCombinations`.

### Criterion 9: Failed/terminal attempts do not consume active Jules concurrency, but Job failure is not treated as successful dependency completion.
- **Status**: Satisfied.
- **Evidence**: `JobPolicy::consumesConcurrency` skips over `isAttemptTerminal` attempts (`src/jobpolicy.h:36`). `JobPolicy::isSuccessfullyComplete` mandates `isAttemptSuccessful` (`src/jobpolicy.h:74`). End-to-end evaluation validated inside `test_queuescheduling.cpp`.

### Criterion 10: Queue/Holding/Blocked/Following/Archive transitions do not destroy or duplicate the only durable task record.
- **Status**: Satisfied.
- **Evidence**: `JobStore` uses transactional atomic file writing (`src/jobstore.cpp:113`). State transitions like archiving (`MainWindow::archiveJobRequested`) update the global job via `m_jobStore->updateJobTransactional(updated)` and emit signals, never destroying or segregating the single `jobs.json` store record. Tested in `test_job.cpp` transactional boundaries.

### Criterion 11: Work is never moved into an Errors model as its lifecycle representation.
- **Status**: Satisfied.
- **Evidence**: Failed sessions mutate `JobAttemptData` tracking errors under `launchErrors` within `JobData`. `ErrorsModel` only handles unattached diagnostics (`ApiError` objects) but no longer owns failing jobs queue entities.

### Criterion 12: The Errors tab is removed once Job/attempt diagnostics and global diagnostics have replacement presentation.
- **Status**: INCOMPLETE / OPEN.
- **Evidence**: The "Errors" tab is still actively instantiated as a core layout panel (`src/mainwindow.cpp:378` `setupErrorsTab`). While errors route properly inside the data models, the visual tab has not been replaced or sunset.
- **Action**: This specific finding necessitates a focused issue since #430 (unified Queue/Blocked) structurally conflicts. The #430 issue alone does not track removal of this tab or replacement global diagnostic presentation. **I have requested/represented this gap to be filed as a focused follow-up issue related to #406 and #430.** (Needs a new issue to track explicit removal of Errors tab).

### Criterion 13: Job detail works sensibly for zero, one, and multiple attempts, while the common single-attempt case remains low-friction.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` logic routes smoothly among `m_zeroAttemptWidget`, `m_singleAttemptWidget`, and `m_multiAttemptWidget` (`src/sessionwindow.cpp:142`). Integrated interactions mocked and tested inside `test_sessionwindow.cpp`.

### Criterion 14: Context menus distinguish new independent Job, new attempt in same Job, variant attempt, retry, archive, and explicit destructive cleanup.
- **Status**: Satisfied.
- **Evidence**: `SessionWindow` actions include exactly: "Launch Variant...", "New Job From This...", "Archive Job", "Delete Job", "Retry". (`src/sessionwindow.cpp:199-240`).

### Criterion 15: Legacy queue/holding/errors/following/archive data is migrated conservatively, atomically, idempotently, and with recovery backups/raw-data preservation.
- **Status**: Satisfied.
- **Evidence**: Handled robustly by `MigrationOrchestrator` backups, `LegacyConverter` parsing, and `JobStore` migrations. Validated fully in `test_legacydatarepair.cpp` and `test_migration_decoupling.cpp`.

### Criterion 16: Existing users do not lose prompts, request settings, error history, session IDs, PR metadata, or retry relationships during migration.
- **Status**: Satisfied.
- **Evidence**: Extracted gracefully into `legacyMetadata` in `JobData::fromJson` (`src/jobdata.cpp:78`).

### Criterion 17: Relevant unit/integration tests cover migration, aggregate state, failed launch, retry, concurrent attempts, winner selection, and queue/sequencing behavior.
- **Status**: Satisfied.
- **Evidence**: Thoroughly verified by integration test suites `test_job.cpp`, `test_migration_decoupling.cpp`, `test_legacydatarepair.cpp`, and `test_queuescheduling.cpp`.

### Criterion 18: Build/format/lint/tests pass via the repository's `.jules/run.sh` environment.
- **Status**: Satisfied. (See Results section).


## 2. #425 Validation Checklist

The following items mandate live-service and interactive UX validation. They remain manually unverified:

- [ ] **Live: Create a new Job and launch its first attempt.**
  *Expected:* Job enters active queue, consumes concurrency slot, launches Jules session, transitions to Pending/Active state.
- [ ] **Live: Launch a concurrent sibling attempt.**
  *Expected:* Original attempt continues undisturbed. New attempt enters active queue, consuming an additional concurrency slot if limits permit.
- [ ] **Live: Launch an edited Variant and confirm the persisted request snapshot matches.**
  *Expected:* Submitted request contains edited payload (e.g. modified prompt) distinct from sibling snapshot.
- [ ] **Live: Retry a failed attempt and confirm the failed sibling remains intact.**
  *Expected:* Old attempt stays preserved holding the error history; a brand new active attempt is placed into the queue.
- [ ] **Live: Choose a completed attempt as winner while another sibling remains active.**
  *Expected:* Job aggregate UI reflects "winner+active" (Winner satisfies requirement, but an outstanding sibling continues).
- [ ] **Live: Pre-session launch failure remains recoverable.**
  *Expected:* Job reflects "Needs Attention" state, retaining data without destroying the core Job item, permitting retry.
- [ ] **Live: Verify PR/result metadata reloads span multiple attempts visually.**
  *Expected:* GitHub webhooks or automatic refreshes update the specific sibling attempt's PR and merge metadata correctly.
- [ ] **Interactive: Delete Job confirmation and transactional removal.**
  *Expected:* Modal dialog appears confirming removal; upon "Yes", Job drops entirely from UI and JSON store.
- [ ] **Interactive: Archive Job and reopening/inspection of archived Jobs.**
  *Expected:* Archived jobs display properly in the Archive tab. Attempting to mutate them triggers constraint blockers.
- [ ] **Interactive: Constraints on mutating archived Jobs.**
  *Expected:* "Launch Variant", "Retry", etc., are disabled or provide errors if invoked against an archived job.
- [ ] **Interactive: Zero-attempt history readability.**
  *Expected:* A Job constructed without any attempts correctly displays its scheduling and configuration parameters clearly.
- [ ] **Interactive: Single-attempt UX friction.**
  *Expected:* Workflow behaves identical to classic Jules single-session windows without heavy multi-tab boilerplate.
- [ ] **Interactive: Unseen/new diagnostic signaling visibility.**
  *Expected:* Status bar notifications or unread counts increment when background operational errors occur.
- [ ] **Persistence: Restart persistence survival.**
  *Expected:* Restarting KJules after queuing a job variant perfectly restores the un-executed job requests.
- [ ] **Persistence: Migrated-data inspection and backup preservation.**
  *Expected:* Reviewing older "converted" jobs from `queue.json` successfully loads properties; the raw backup files exist intact.
